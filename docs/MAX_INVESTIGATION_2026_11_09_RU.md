# MAX: обычная группа без бота — проверка 9 ноября 2026

**Повторная проверка 12 ноября 2026:** получена официальная схема по той же ссылке, версия `0.0.34`, HTTP 200, 127 268 байт. В ней `GET /messages` по-прежнему относится к Bot API, предел страницы 1–100, временные границы `before/after`; для групповых обновлений указано право `read_all_messages`. Гарантии полной истории обычного участника или сообщений до добавления бота не обнаружено. `help.max.ru` и `dev.max.ru/docs-api` недоступны через прокси этой среды (`ProxyError`). Возможность экспорта в конкретной версии пользовательского клиента остаётся неподтверждённой. Пилот на настоящем фрагменте группы пока не выполнен.

Для существующей группы примерно на семь участников основной путь — получение доступной истории участником через официальный клиент или официальный экспорт, если он действительно есть. Добавлять бота ради этого не предлагается. Доступа к вашей группе в облачной среде нет; полный экспорт и получение настоящих вложений здесь не проверены.

## Что подтверждено и что неизвестно

| Вопрос | Результат проверки |
| --- | --- |

| Что удалось получить из официальных источников? | [Схему Max Bot API](https://github.com/max-messenger/api-schema/blob/main/schema.yaml) из официального репозитория: HTTP 200, 126 817 байт, версия `0.0.33`. |
| Даёт ли Bot API права обычного участника? | Нет такого основания в проверенной схеме. Она прямо описывает ботов, авторизацию токеном бота и ошибки отсутствия доступа. Групповые обновления требуют права администратора `read_all_messages`. |
| Гарантирована ли история до добавления бота? | Такой гарантии в проверенной схеме нет. Наличие временных параметров `before/after` само по себе её не создаёт. |
| Даёт ли выдача персональных данных все сообщения других участников и их вложения? | Не подтверждено. Нужна официальная инструкция и проверка фактического состава архива. |
| Проверен ли локальный сбор через интерфейс MAX? | Оценён как возможный запасной путь, но не испытан на авторизованном клиенте и настоящей группе. Селекторы сообщений, правила загрузки вложений и доступность старой истории не установлены. Готовый «сборщик всей истории» не заявляется. |

Официальные страницы для повторной проверки вне ограничения этой среды: [справка MAX](https://help.max.ru/), [получение сообщений Bot API](https://dev.max.ru/docs-api/methods/GET/messages), [права бота в чатах](https://dev.max.ru/docs-api/use-cases/bot-in-chats-and-channels). Доступная схема подтверждает только договор Bot API; она не заменяет руководство обычного клиента.

## Небольшой пилот до попытки собрать несколько лет

Понадобится компьютер с официальным клиентом MAX и доступом участника к этой группе. Вход выполняется самим пользователем локально. Пароли, коды входа, cookies и токены сессии в чат не передаются.

1. Установить платформу и версию клиента: Windows, браузер либо мобильное приложение; роль участника или администратора группы. Проверить, есть ли в этой версии официальный экспорт истории или выдача данных, и что именно он содержит. Не переименовывать неизвестный ZIP в JSON.
2. Выбрать короткий известный фрагмент: примерно 10–20 сообщений, включая ответ на сообщение, одну фотографию, одно видео и один документ. Полезно включить два сообщения с одинаковым текстом: проверка не должна ошибочно слить их в одно.
3. Если официальный экспорт доступен, получить только этот фрагмент либо выделить его копию из полученного архива. Если экспорта нет, проверить доступные операции официального интерфейса: чтение нужного периода и сохранение оригинальных вложений. Автоматизацию выбирать только после этой проверки.
4. Сверить каждую запись с клиентом: автор, время и его часовой пояс, текст, идентификатор сообщения/чата и ссылка ответа. Если интерфейс не даёт идентификатор или время, записать `неизвестно`. Не подставлять порядок строк вместо родного ID или дату скачивания вместо даты сообщения.
5. Сохранить именно оригиналы вложений. Миниатюра фотографии и кадр видео не считаются исходным файлом. Для каждого файла проверить открытие, размер, SHA-256 и связь с сообщением; отметить недоступные, удалённые или нескачанные файлы.
6. Прервать получение после нескольких сообщений и повторить запуск. Сравнить состав записей, повторные файлы и отчёт о пропусках. Только после успешного пилота выбирать способ расширения периода.

Для настоящего пилота пока не хватает версии/платформы клиента и легально полученного фрагмента с оригиналами вложений. Скриншоты не заменяют эти файлы и связи. Если клиент не предоставляет структурированный экспорт, сначала нужен локальный просмотр его доступных операций; извлечение сессионных секретов или вход из облака не требуется.

## Ограничения сбора через пользовательский интерфейс

Автоматизация видимого интерфейса может обработать только то, что официальный клиент реально показывает авторизованному участнику. Она не восстанавливает удалённые сообщения, старые недоступные вложения или историю, которую клиент не загрузил.

До реального пилота необходимо проверить:

- Виртуализацию списка: прокрутка может удалять старые строки из DOM. Один снимок страницы не содержит всю историю.
- Ленивую подгрузку: отсутствие строк при прокрутке не доказывает достижение начала чата.
- Устойчивость признаков сообщений, авторов, дат и ответов. Непроверенные CSS-селекторы не являются готовым интерфейсом экспорта.
- Наличие родных ID. Если их нет, локальный отпечаток текста и времени — лишь подсказка о возможном дубле. Два одинаковых сообщения нельзя автоматически считать одной записью.
- Скачивание файлов: открытие превью не всегда означает сохранение оригинала; ссылки могут истекать, а файлы — отсутствовать.
- Продолжение после сбоя: позиция прокрутки не является надёжной контрольной точкой. Нужен журнал уже сохранённых родных ID, файлов и нерешённых пропусков.

В этом обновлении не добавлен неподтверждённый DOM-экспортёр MAX. Сначала проверяется доступный официальный интерфейс на коротком фрагменте, затем можно реализовать адаптер именно для наблюдаемой версии клиента.

## Переносной архив POSTEKS с оригинальными вложениями

Импортёр использует собственный договор ZIP `posteks.archive.v1`. Это **не формат официального экспорта MAX**. Преобразование из настоящего экспорта выполняется с сохранением исходных данных и только после проверки его структуры.

Пример структуры; все имена и идентификаторы ниже фиктивные:

```text
sample.zip
  manifest.json
  files/photo.jpg
  files/video.mp4
  files/manual.pdf
```

```json
{
  "schema": "posteks.archive.v1",
  "source": "MAX",
  "messages": [
    {
      "id": "example-native-message-id",
      "conversation_id": "example-native-chat-id",
      "date": "2026-11-01T10:00:00+05:00",
      "sender": "Пример автора",
      "text": "Тестовое описание симптома",
      "reply_to_id": null,
      "attachments": [
        {"path": "files/photo.jpg"},
        {"path": "files/video.mp4"},
        {"path": "files/manual.pdf"}
      ]
    }
  ],
  "coverage": {"completeness": "unknown"}
}
```

Пути указывают на файлы внутри ZIP. Сетевые URL и токены не заменяют скачанные оригиналы. Если родного ID или автора нет, это неизвестное поле, а не повод выдумывать значение. Исходный архив сохраняется; материалы остаются внутренней непроверенной историей. Архивная просьба «отправить счёт» и ответ «отправили» не запускают сегодняшние действия и не подтверждают сегодняшнюю отправку.

## Четыре отдельных результата проверки

| Этап | Что он доказывает |
| --- | --- |
| Сообщения получены | Записи сохранены, известные автор/время/ID/ответы связаны; отсутствие полей и пропуски отмечены. |
| Вложения сохранены | Оригинальные файлы присутствуют и проверены; ссылка или превью не засчитываются как файл. |
| Содержимое обработано | Для конкретного файла завершено извлечение текста/OCR/поддерживаемая обработка. Неудача видео не равна отсутствию видео. |
| Доступно поиску | Есть построенный доступный индекс. Это не означает, что материал стал подтверждённым решением или разрешён клиентам. |

Повтор одинакового ZIP должен определяться по хешу. Перекрывающиеся партии дополнительно сравниваются по исходным ID и связанным файлам. Повторная индексация после сбоя не должна создавать новые сообщения. Если ID не известны, отчёт должен отражать невозможность надёжно доказать отсутствие повторов.

Полнота всей группы остаётся `unknown`, пока не сверены начало и конец периода, число сообщений, пропуски, ограничения клиента и вложения. Успешный импорт отдельной партии не является завершённой выгрузкой всех лет.
